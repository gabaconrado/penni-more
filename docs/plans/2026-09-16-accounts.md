# Accounts

## Summary

Add the first financial domain object as a server-rendered, authenticated Accounts feature. Every
account has one immutable owner, a required name, an optional description, and a Bank or Card
type. Owners can create, view, edit, permanently delete, share, and revoke access. Recipients can
discover and view shared accounts but cannot change account information or sharing.

The feature uses Django forms and views, existing session authentication, Tailwind/DaisyUI
templates, and no JavaScript or new dependency. It adds no JSON endpoint or OpenAPI operation.

## Goals

- Persist accounts with an immutable owner and type restricted to Bank or Card.
- Give authenticated users full CRUD over accounts they own.
- Let owners grant or revoke read-only access for one existing user email at a time.
- Present owned and shared accounts together without duplicate rows and with an explicit access
  indicator.
- Prevent shared recipients and unrelated users from reaching owner-only behavior through direct
  requests.
- Deliver accessible, responsive account pages that preserve server-side errors and work without
  JavaScript.
- Cover model invariants, authorization, persistence, forms, routes, rendered states, and
  accessibility through backend and Web GUI tests and reviews.

## Non-goals

- Transactions or allowing any account recipient to create them. The confirmed future rule is that
  recipients may add transactions, but transaction authorization and persistence belong to that
  feature.
- Balances, currency, money precision, rounding, signs, transaction dates, or account statements.
- Pending invitations, outbound email, bulk sharing, user search, or autocomplete.
- Editable collaborators, ownership transfer, soft deletion, restoration, or audit history.
- REST or JSON account operations and any OpenAPI account schema.
- Pagination, search, filtering, or sorting controls for this initial personal-use collection.
- Django admin management for accounts.

## User-visible behavior

- An authenticated user can follow the single **Accounts** navigation link to `/accounts/`.
- The accounts page shows every owned and shared account once in stable name order. Its table has
  Name, Description, Type, and Access columns; Access says Owner or Shared. Account names link to
  their detail pages. A **Create account** action appears above the table, and a useful empty state
  replaces the table when no account is accessible.
- Any authenticated user can create an account. Name is required, description is optional, Bank
  and Card are the only type choices, and duplicate names are accepted. The server assigns the
  current user as owner; no owner input is rendered or accepted.
- An account detail page shows its name, description, human-readable type, access level, and owner
  email. A missing description has deliberate fallback copy rather than a blank ambiguous region.
- The owner additionally sees edit and delete actions, a one-email share form, and the current
  recipients with an individual revoke action. A recipient sees none of those controls and cannot
  see other recipients.
- Sharing accepts one email per submission and matches the existing canonical email identity
  without case sensitivity. Unknown email, the owner's own email, and a user who already has access
  each produce a clear error on the detail page without creating a relationship or discarding the
  submitted value.
- A successful share or revoke returns to the account detail and displays a status message. A
  successful create or edit returns to the account detail. The edit form exposes only name,
  description, and type.
- Delete first displays a confirmation page naming the account and explaining that deletion is
  permanent. Only its CSRF-protected POST performs deletion, including deletion of all sharing
  records, then returns to the account list with a status message.
- Every account route requires authentication. Requests for an inaccessible account or an
  owner-only route by a recipient or unrelated user return 404 so they do not disclose whether the
  account exists. Unsupported methods do not change state.

## Decisions and assumptions

- Add a cohesive `penni_more.accounts` Django application. Store types as stable lowercase values
  `bank` and `card` through `models.TextChoices`, while forms and pages display Bank and Card.
- Use `Account.name` as a `CharField(max_length=255)`, `description` as a blank-allowed
  `TextField`, `account_type` as the choices field, and a non-null `owner` foreign key to
  `settings.AUTH_USER_MODEL`. Names are not unique and whitespace-only names are rejected by the
  model form's required text handling.
- Use `on_delete=models.CASCADE` for the owner relationship: if an operator deliberately deletes a
  user, records owned solely by that identity cannot remain ownerless. This feature adds no user
  deletion flow. The account model rejects changing `owner_id` after creation; all account forms
  exclude the owner and creation takes it only from `request.user`.
- Represent sharing with an explicit `AccountShare` model containing non-null account and recipient
  foreign keys. Add a named database unique constraint over `(account, recipient)` and cascade
  shares when either referenced record is deleted. Application validation rejects sharing with the
  owner; the service repeats duplicate handling at write time so a validation race does not surface
  as an unhandled database exception.
- Centralize `Account` visibility in an accessible-account queryset that filters for owner or share
  recipient, calls `distinct()`, and orders by `name`, then primary key. Owner-only views query by
  both primary key and `request.user` ownership instead of fetching first and returning 403.
- Keep views thin. `AccountForm` owns name, description, and type boundary validation;
  `AccountShareForm` accepts only email and resolves an existing recipient case-insensitively.
  A focused sharing service creates and revokes `AccountShare` rows and handles the final duplicate
  check. No user enumeration endpoint is introduced.
- Django's installed `LoginRequiredMiddleware` protects the new routes by default. Do not add a
  `login_not_required` exemption. All state changes use POST plus Django CSRF protection; delete
  alone also has a read-only GET confirmation page.
- Django's messages framework supplies success feedback. Form failures render associated inline
  errors and an error summary where useful. User content remains autoescaped.
- Shared recipients are read-only only with respect to the shared account. Like every authenticated
  user, they may create a separate account that they own.
- No timestamps are required for Account or AccountShare because the approved behavior neither
  displays nor orders by them. The primary key is the stable tie-breaker for deterministic lists.

## Contract impact

There is no OpenAPI impact. The existing contract describes only JSON health endpoints. Accounts
are private server-rendered HTML pages submitted through ordinary HTML forms, so adding them to the
OpenAPI document would inaccurately expand the API surface. Existing health paths, schemas, and
security declarations remain unchanged.

The internal HTML route interface is:

| Method | Path | Route name | Authorization and result |
| --- | --- | --- | --- |
| GET | `/accounts/` | `accounts:list` | Authenticated; all distinct accessible accounts |
| GET, POST | `/accounts/new/` | `accounts:create` | Authenticated; creates an account owned by the requester |
| GET | `/accounts/<int:pk>/` | `accounts:detail` | Owner or recipient; otherwise 404 |
| GET, POST | `/accounts/<int:pk>/edit/` | `accounts:update` | Owner only; otherwise 404 |
| GET, POST | `/accounts/<int:pk>/delete/` | `accounts:delete` | Owner only; GET confirms and POST permanently deletes |
| POST | `/accounts/<int:pk>/share/` | `accounts:share` | Owner only; validates one email, otherwise 404 |
| POST | `/accounts/<int:pk>/shares/<int:share_id>/revoke/` | `accounts:revoke` | Owner and nested share only; otherwise 404 |

`AccountForm` submits `name`, `description`, and `account_type`. `AccountShareForm` submits only
`email`. Revoke submits no domain field; account and share identifiers come from the nested route.
All forms include CSRF metadata.

The list context provides `accounts`. Detail provides `account`, `is_owner`, and, only for the
owner, `share_form` and `shares` with recipient users already loaded. Invalid sharing renders the
same detail template and status 200 with bound errors. Form pages provide `form` and a create/edit
mode or equivalent heading/action context. Delete confirmation provides `account`.

Use redirects after successful POST to prevent accidental resubmission: create, update, and share
redirect to `accounts:detail`; revoke redirects to the same detail; delete redirects to
`accounts:list`. Route code must not rely on template hiding for authorization.

## Implementation sequence

1. The backend coder creates the accounts application, installs it, and implements `Account`, its
   choices and accessible queryset, and `AccountShare` with the approved foreign keys and database
   uniqueness. Add model validation for immutable ownership and self-sharing, then generate the
   initial migration.
2. The backend coder adds model tests for field requirements, allowed types, duplicate names,
   immutable ownership, self-sharing, unique shares, cascade behavior, accessible-query
   de-duplication, and deterministic ordering.
3. The backend coder implements `AccountForm`, `AccountShareForm`, and the small sharing service.
   Case-insensitive lookup must follow the existing canonical email identity; unknown, self, and
   duplicate cases must remain distinguishable form errors without leaking an exception from a
   concurrent duplicate.
4. The backend coder includes the namespaced account routes and implements list, create, detail,
   update, delete, share, and revoke views. Use an accessible queryset for read detail and an
   owner-filtered queryset for every owner-only object lookup. Assign the owner from the request and
   preload owner/share recipient data needed by each page.
5. In parallel with steps 1-4, the Web GUI coder builds the fixed templates and navigation
   interface. Cover the empty list, responsive account table, shared-versus-owner detail states,
   bound form errors, recipients, CSRF POST controls, and delete warning without JavaScript.
6. The backend coder adds request tests across successful and invalid methods, anonymous redirects,
   owner behavior, recipient read-only behavior, unrelated-user 404 behavior, form errors,
   messages, CSRF enforcement, escaped user content, and redirect targets. The Web GUI coder adds
   template structure tests plus browser-visible anonymous route protection and accessible page
   checks that can be supported without adding account provisioning infrastructure.
7. Each coder runs `.codex/lint.sh` and their scoped checks. The backend reviewer and Web GUI
   reviewer then review their respective scopes. Every actionable finding returns to the owning
   coder, and review repeats until neither reviewer reports a blocking finding.
8. The architect compares the integrated routes, contexts, form fields, authorization, and

   health-only scope is still accurate.
9. The deployment agent runs final repository and migration checks, creates the justified local
   commit or commits, and later commits the feature report under `docs/reports` if it is produced
   separately.

## Review and verification

### Backend review

Tests and review must demonstrate:

- Account requires a non-empty name and accepts a blank description; only `bank` and `card` persist,
  and duplicate names are valid.
- Every account has one owner assigned from the authenticated request. Account forms and submitted
  extra fields cannot select or replace it, and model-level saves cannot transfer an existing
  account.
- A share requires an existing case-insensitively matched user, rejects the owner, and cannot be
  duplicated through either normal validation or a database-level bypass. Account deletion removes
  its shares.
- The list returns each owned or shared account once in `name`, primary-key order and exposes no
  unrelated account. Queries avoid per-row owner lookups and detail avoids per-recipient lookups.
- Detail is available to owner and recipient. Recipients and unrelated users receive 404 from edit,
  delete, share, and revoke direct requests; unrelated users also receive 404 from detail.
- The recipient detail context contains no recipient collection. Only the owner detail context and
  rendered response expose current recipients.
- Create, update, delete, share, and revoke obey their allowed methods, use CSRF-protected POST for
  state changes, redirect after success, and leave persistence unchanged on invalid requests.
- Invalid account fields and unknown, self, or duplicate share emails return usable bound errors.
  A revoke identifier from another account cannot be deleted through a mismatched nested URL.
- User-provided name, description, and email content is escaped in rendered HTML.

## Risks

- Hiding owner controls in templates is not authorization. Every owner-only route must resolve from
  an owner-filtered queryset and return 404 for a recipient or unrelated identifier.
- Joining accounts to shares can duplicate list rows. The accessible queryset requires `distinct()`
  and a stable two-field ordering; tests must include more than one share.
- Share form validation can race with another submission. The database uniqueness constraint is the
  final invariant, and the service must turn the losing duplicate into the approved user-facing
  outcome rather than expose `IntegrityError`.
- Self-sharing cannot be expressed as a simple cross-table database check because ownership lives
  on Account. Model/form/service validation is required, and no bulk sharing write path is added.
- Recipient privacy can be lost by reusing the owner detail context. Build owner-only recipient
  context deliberately and test response content with multiple distinct recipient emails.
- Permanent deletion will later need transaction semantics. This cycle cascades only sharing rows;
  the transaction feature must explicitly decide whether accounts with transactions may be deleted
  and what happens to those records.
- A horizontally wide table can be unusable on a phone. Confine horizontal scrolling to a labeled
  table wrapper and keep actions outside the table rather than shrinking text or requiring script.

## Deferred work

Transactions, including the confirmed permission for shared recipients to add them and the effect
of account deletion on transaction history, are deferred to the transaction feature. The same
future design must define balances, currency, precision, rounding, signs, and date semantics before
introducing money fields. No task artifact is needed yet because these are explicit non-goals, not
defects in the Accounts feature.

Pending invitations, bulk sharing, searchable users, editable collaborators, ownership transfer,
soft deletion, audit history, pagination, filtering, and an Accounts API likewise remain outside
this cycle and have no current acceptance dependency.

## Completion criteria

- A reviewed migration creates Account and AccountShare with the approved ownership, type, cascade,
  and uniqueness invariants, and Django reports no missing migrations.
- Authenticated users can create, list, view, edit, and permanently delete owned accounts through
  the server-rendered interface; owner identity is never accepted from user input.
- Owners can share with and revoke one existing non-owner user by case-insensitive email, with clear
  unknown, self, and duplicate handling and no duplicate persistence.
- The combined list contains each accessible account once with Name, Description, Type, and
  Owner/Shared status. Detail exposes recipient identities and mutation controls only to the owner.
- Recipient and unrelated direct requests enforce the approved read-only and non-disclosure rules,
  including nested revoke authorization.
- All pages and forms are responsive, accessible, CSRF protected, autoescaped, and functional
  without JavaScript.
- OpenAPI remains unchanged and accurate for its existing health-only JSON surface; no new
  dependency or deployment change is introduced.
- Backend, Web GUI, and architect reviews report no unresolved blocking findings.
- `.codex/lint.sh`, scoped checks, migration verification, and `./penni-more.sh check all` pass with
  observed results.
- The implementation report is written and the deployment agent alone creates the justified local
